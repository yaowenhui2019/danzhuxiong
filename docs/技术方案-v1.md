## 一、整体系统架构

### 1.1 架构总览

```
┌──────────────────────────────────────────────────────────────┐
│  客户端：原生微信小游戏（minigame/）                            │
│  ┌─────────┐ ┌─────────┐ ┌──────────┐ ┌─────────────────┐   │
│  │ 场景路由 │ │ Canvas  │ │ Recorder │ │ InnerAudio      │   │
│  │  app.js │ │  UI     │ │ Manager  │ │ Context（单例）  │   │
│  └─────────┘ └─────────┘ └──────────┘ └─────────────────┘   │
└───────────────────────────┬──────────────────────────────────┘
                            │ HTTPS  JSON / multipart
┌───────────────────────────▼──────────────────────────────────┐
│  服务端：FastAPI 单进程（server/）                              │
│  ┌────────────────────────────────────────────────────────┐  │
│  │ API 层  main.py                                         │  │
│  │  /api/game/start  /api/game/act  /api/asr  /api/tts    │  │
│  └───────┬──────────────────┬──────────────────┬──────────┘  │

│  ┌───────▼────────┐ ┌───────▼────────┐ ┌───────▼──────────┐  │
│  │ 游戏引擎        │ │ AI 层          │ │ 语音层            │  │
│  │ engine.py      │ │ ai.py          │ │ voice.py          │  │
│  │ 权威状态机      │ │ LLM + 兜底     │ │ VoiceProvider 抽象│  │
│  └───────┬────────┘ └───────┬────────┘ └───────┬──────────┘  │
│          │                  │                  │             │
│  ┌───────▼──────────────────▼──────────────────▼──────────┐  │
│  │ 会话存储  store（内存 dict，进程内）                      │  │
│  └────────────────────────────────────────────────────────┘  │
└───────────────┬──────────────────────────────┬───────────────┘
                │                              │
      ┌─────────▼─────────┐          ┌─────────▼─────────┐
      │ 灵矽平台（A1/A2）   │          │ LLM 网关          │
      │ WSS 虚拟设备        │          │ OpenAI 兼容       │
      │ ASR / TTS / 音色库  │          │ 七牛 / DeepSeek   │
      └───────────────────┘          └───────────────────┘

      兜底路径（B）：faster-whisper（本地 ASR） + edge-tts（本地 TTS）
```

### 1.2 架构原则

| 原则 | 落地方式 |
|---|---|
| **服务端权威** | 身份、牌局、投票全部在服务端；客户端只拿到自己的身份和公开信息 |
| **语音可插拔** | `VoiceProvider` 抽象出 `asr()` / `tts()`；灵矽与本地兜底可运行时切换 |
| **大脑可插拔** | `LLMProvider` 抽象；无 key 时退化为模板大脑，demo 永不空场 |
| **失败可降级** | 每一层都有兜底：语音→本地、LLM→模板、麦克风→打字 |
| **单进程够用** | 单人局、并发个位数，不引入 Redis / 消息队列 / 微服务 |

### 1.3 技术选型

| 层次 | 选型 | 理由 | 被否掉的方案 |
|---|---|---|---|
| 客户端框架 | **原生小游戏**（无引擎） | 只有圆桌 + 按钮 + 音频，包体可压到 2MB 内，秒开 | Cocos Creator（首包 8MB+，冷启动 3s+） |
| 渲染 | Canvas 2D + `requestAnimationFrame` | 4 个界面、无骨骼动画、无物理 | 引擎场景系统 |
| 音频播放 | `InnerAudioContext` 单例 | 原生支持 mp3 URL，无需解码 | WebAudio（小游戏无实时流） |
| 录音 | `RecorderManager` 整段录制 | 小游戏唯一可用录音通道 | `onFrameRecorded` 流式（首版不用） |
| 服务端 | **Python 3.13 + FastAPI** | ASR/TTS/LLM 生态同语言，改写 prompt 与调参最快 | Node/Express（音频处理库弱） |
| 状态机 | 单进程内存 + 显式 `phase` 枚举 | 一局 5 分钟，无需持久化 | Redis / 数据库（过度设计） |
| LLM | OpenAI 兼容 HTTP | 七牛网关、DeepSeek 都能直连，换模型只改 env | 厂商 SDK（锁定） |
| TTS（A2） | 灵矽音色库 | 5 个 AI 各一条声线，且是议题要求 | — |
| TTS（B） | edge-tts | 免费、零 key、8 个 zh-CN 音色、已实测 | 系统 TTS（小游戏没有） |
| ASR（A1） | 灵矽设备协议 | 议题要求 | — |
| ASR（B） | faster-whisper small | 本地、离线、中文可用 | 云端 ASR（要 key） |
| 音频格式 | mp3 over HTTP | `InnerAudioContext` 直接吃 | opus（需自行解码，客户端做不到） |

## 二、核心模块划分及职责

### 2.1 服务端

| 模块 | 文件 | 职责 | 不做什么 |
|---|---|---|---|
| **API 层** | `server/main.py` | 路由、入参校验、异常包装、静态音频服务、会话表 | 不含任何游戏规则 |
| **游戏引擎** | `server/engine.py` | 角色分配、阶段流转、发言队列、投票裁决、胜负判定 | 不直接调 LLM/TTS，只调抽象 |
| **AI 层** | `server/ai.py` | 人格 prompt 组装、LLM 调用、上下文裁剪、模板兜底 | 不碰音频 |
| **语音层** | `server/voice.py` | `VoiceProvider` 抽象、TTS 缓存与重试、ASR 转写 | 不懂游戏状态 |
| **灵矽客户端** | `server/linx.py`（待实现） | WSS 虚拟设备、hello 握手、PCM 分帧、Opus 解码 | 不含业务逻辑 |

### 2.2 客户端

| 模块 | 文件 | 职责 |
|---|---|---|
| 入口 | `minigame/game.js` | 创建 canvas、绑定触摸、启动 rAF 主循环 |
| 场景与状态 | `minigame/js/app.js` | 场景路由（首页/圆桌/战报）、调用 API、驱动播放流水线 |
| 绘制 | `minigame/js/ui.js` | 圆桌、座位、说话高亮、麦克风 HUD、战报 |
| 网络 | `minigame/js/api.js` | `wx.request` 封装、`wx.uploadFile` 上传录音 |
| 播放 | `minigame/js/audio.js` | 单例 `InnerAudioContext`、播放队列 |
| 录音 | `minigame/js/recorder.js` | 按住录、松手传、时长保护 |
| 配置 | `minigame/js/config.js` | `BASE_URL` |

### 2.3 模块依赖方向

```
app.js ──► ui.js
   │  └──► api.js ──► config.js
   └─────► audio.js / recorder.js

main.py ──► engine.py ──► ai.py
                │            │
                └──► voice.py ◄┘
                        │
                        └──► linx.py（可选）
```

**规则**：依赖单向向下，`voice.py` 不 import `engine.py`，避免循环。

## 三、关键业务流程与数据流

### 3.1 开局（F1）

```
客户端 POST /api/game/start {role?: "wolf"|"seer"|"villager"}
  └─► main.py 生成 game_id = uuid4().hex[:8]
       └─► engine.Game.new(): 6 座位固定，角色池洗牌分配
            └─► game.start(): 生成 2 段上帝播报 → TTS
                 └─► 返回 {audios, prompt, state}
                      ├─ audios: 天黑请闭眼 / 狼人请睁眼
                      └─ prompt: 若真人是狼 → 选择击杀目标
```

### 3.2 玩家语音发言（F4，核心链路）

```
① 按下麦克风  → recorder.start()  RecorderManager 开始录音
② 松手        → recorder.stop()   → onStop 得到 tempFilePath
③ 上传        → POST /api/asr (multipart)
                 └─► voice.transcribe(): faster-whisper 或 灵矽 stt
④ 拿到文本    → POST /api/game/act {action:"speak", text:"我觉得3号有问题"}
⑤ 服务端      → engine.next_speech(human_text) 写入 log，进入下一个 AI 的回合
⑥ 客户端      → 显示玩家发言气泡
```

**关键约束**：录音短于 0.8s 直接丢弃，避免把呼吸声送去识别。

### 3.3 AI 发言流水线（性能关键）

问题：5 个 AI × (LLM 2s + TTS 1s) = 15s 冷场。

解法：**服务端串行生成 + 客户端预取一条**。

```
时序：
t=0   客户端 POST /act next           → 服务端生成 AI-1（LLM 2s + TTS 1s）
t=3   收到 AI-1 音频（时长 ~8s），立即播放，同时立刻 POST /act next 预取 AI-2
t=3~11 播放 AI-1 ← 这 8 秒里 AI-2 早就生成好了
t=11  AI-2 直接播，同时预取 AI-3
```

效果：除首句外，段间空档接近 0。

**为什么串行而不是并行**：狼人杀的乐趣在"互相咬"。第 3 个 AI 必须能看到第 2 个 AI 说了什么。并行会变成 5 段各说各的独白。

### 3.4 投票与结算（F5）

```
POST /act {action:"vote", target:3}
  ├─ 真人票：target
  ├─ AI 票：启发式 _ai_vote()
  │    ├─ 狼人：优先投好人民
  │    └─ 所有人：统计 log 里 "N号" 被提及次数，取最高
  ├─ 计票：平票 → 无人出局
  ├─ 出局者 alive=false，写入 deaths
  └─ _check_win(): 狼 0 → 好人胜；狼 ≥ 好 → 狼胜；否则进入下一天
```

### 3.5 状态流转图

```
        start
          │
          ▼
   ┌─────────────┐  真人不是狼，AI 自动下刀
   │ night_wolf  │──────────────┐
   └──────┬──────┘              │
          │ 真人选目标            │
          ▼                     │
   ┌─────────────┐              │
   │ night_seer  │ 只有真人是预言家才进入
   └──────┬──────┘              │
          └────────┬────────────┘
                   ▼
            ┌─────────────┐
            │  day_speak  │◄──────────┐
            └──────┬──────┘           │
                   │ 发言队列空         │ 未分胜负
                   ▼                  │
            ┌─────────────┐           │
            │  day_vote   │───────────┘
            └──────┬──────┘
                   │ 分出胜负
                   ▼
            ┌─────────────┐
            │    over     │──► finale（复盘语音）
            └─────────────┘
```

### 3.6 数据流全景

```
录音 ──► ASR ──► 文本 ──► log[] ──► LLM 上下文 ──► AI 台词 ──► TTS ──► mp3 ──► 播放
                              ▲
                       public_state()
                              │
                       客户端渲染圆桌
```

## 四、接口设计

统一约定：`Content-Type: application/json`，错误返回 `{"error": "..."}` + 非 200 状态码。

### 4.1 `POST /api/game/start`

| 参数 | 类型 | 必填 | 说明 |
|---|---|---|---|
| `role` | string | 否 | 调试用，强制真人身份：`wolf` / `seer` / `villager` |

```json
{
  "audios": [{"text":"天黑请闭眼。","voice":"narrator","speaker":-1,"kind":"narrator","url":"/audio/ab12.mp3"}],
  "prompt": {"type":"pick_target","title":"今晚杀谁？","hint":"点一个头像，或直接说“杀3号”","candidates":[1,2,3,4,5]},
  "state": {
    "game_id":"9f3a1c2b","phase":"night_wolf","day":1,
    "you":{"id":0,"role":"wolf","role_name":"狼人","alive":true},
    "players":[{"id":0,"name":"你","alive":true,"is_you":true,"role_name":"狼人"},
               {"id":1,"name":"老张","alive":true,"is_you":false,"role_name":null}],
    "deaths":[],"winner":null,"log":[]
  }
}
```

> **身份保密**：`players[].role_name` 除了 `is_you` 的座位，其他一律为 `null`，只有 `phase === "over"` 时才全量揭晓。

### 4.2 `POST /api/game/act`

| 参数 | 类型 | 必填 | 说明 |
|---|---|---|---|
| `game_id` | string | 是 | 开局返回的 id |
| `action` | string | 是 | `wolf_kill` / `seer_check` / `next` / `speak` / `vote` / `finale` |
| `target` | int | 否 | 目标座位号 |
| `text` | string | 否 | 真人发言文本、或语音投票的原始文本 |

| action | 语义 | 必需字段 |
|---|---|---|
| `wolf_kill` | 狼人选择击杀 | `target` 或 `text` |
| `seer_check` | 预言家查验 | `target` 或 `text` |
| `next` | 取下一段 AI 发言（用于预取） | — |
| `speak` | 提交真人发言 | `text` |
| `vote` | 投票 | `target` 或 `text` |
| `finale` | 生成复盘 | — |

响应结构同 4.1（`audios` / `prompt` / `state`）。

**文本容错**：`parse_target()` 支持"我投3号 / 杀四号 / 3"，中文数字与阿拉伯数字都认。

### 4.3 `POST /api/asr`

`multipart/form-data`，字段 `file`，返回：

```json
{"text": "我觉得三号有问题"}
```

### 4.4 `POST /api/tts`

```json
// 请求
{"text":"天黑请闭眼。","voice":"narrator"}
// 响应
{"url":"/audio/ab12cd34.mp3"}
```

### 4.5 `GET /api/health`

```json
{"ok":true,"llm":true,"model":"deepseek-v3"}
```

用于启动自检：`llm=false` 说明在跑模板兜底。

### 4.6 `GET /audio/{filename}`

静态 mp3。文件名为 `md5(voice|text)` 前 16 位，天然幂等去重。

## 五、数据模型设计

### 5.1 服务端实体

```python
Player
├─ id: int            # 座位号 0-5，0 固定为真人
├─ name: str          # 你 / 老张 / 阿May / 大熊 / 小七 / 老K
├─ voice: str         # 音色 key（narrator / p1..p5）
├─ persona: str       # 人格描述，直接进 system prompt
├─ role: str          # wolf / seer / villager
└─ alive: bool

Game
├─ game_id: str       # uuid 前 8 位
├─ players: list[Player]
├─ day: int           # 从 1 开始
├─ phase: str         # init/night_wolf/night_seer/day_speak/day_vote/over
├─ log: list[{id, name, text}]        # 公开发言流水，喂给 LLM
├─ deaths: list[{id, name, role, night}]
├─ votes: dict[int, int]              # 投票人 → 被投人
├─ wolf_target: int | None
├─ seer_result: {target, is_wolf} | None
├─ winner: "good" | "wolf" | None
└─ speak_queue: list[int]             # 本日尚未发言的座位
```

### 5.2 角色配置

| 座位 | 名字 | 音色 | 人格 |
|---|---|---|---|
| 0 | 你 | — | 真人 |
| 1 | 老张 | p1 | 逻辑流，盘时间线和票型 |
| 2 | 阿May | p2 | 情绪流，语速快、易激动 |
| 3 | 大熊 | p3 | 和事佬，谁都不想得罪 |
| 4 | 小七 | p4 | 阴阳怪气，爱反讽 |
| 5 | 老K | p5 | 话少刀狠 |

**角色池**：`[wolf, wolf, seer, villager, villager, villager]`，开局 `random.shuffle` 后按座位分配。

### 5.3 阶段与可执行动作

| phase | 允许的 action | 说明 |
|---|---|---|
| `night_wolf` | `wolf_kill` | 真人是狼才需要他操作 |
| `night_seer` | `seer_check` | 真人是预言家才进入 |
| `day_speak` | `next` / `speak` | `next` 推进 AI，`speak` 提交真人发言 |
| `day_vote` | `vote` | — |
| `over` | `finale` | — |

> **服务端必须校验 action 与 phase 匹配**，否则恶意客户端可以跳过发言直接投票。

### 5.4 客户端状态

```js
{
  scene: 'home' | 'table' | 'over',
  state: <服务端 state 原样>,
  nextClip: Clip | null,      // 预取的下一条音频
  pendingPrompt: Prompt|null, // 等音频播完才展示
  speakingId: number | -1,    // 当前高亮座位
  recording: boolean,
  toast: string
}
```

### 5.5 存储策略

| 数据 | 位置 | 生命周期 | 理由 |
|---|---|---|---|
| 对局状态 | 进程内存 `GAMES: dict` | 服务重启即失效 | 单人局，5 分钟，不需要持久化 |
| TTS 音频 | `server/audio/*.mp3` | 保留到当天结束 | 固定台词（上帝播报）跨局复用，命中率高 |
| 录音临时文件 | 系统临时目录 | 转写后立即删除 | 隐私：不留用户声音 |
| 战绩 | 不落库 | — | P2，已被砍 |

## 六、关键技术难点及解决方案

### 难点 1：小游戏做不了实时全双工语音

**问题**：小游戏沙箱无 WebAudio 实时流，`RecorderManager` 只能整段录制，`InnerAudioContext` 只能播完整文件。端到端延迟必然 1.5–3 秒。

**解法**：不改技术，改玩法。
- 产品形态定为**回合制**（发言本来就是一个一个人说），消除"打断"需求
- UI 用"按麦→波形→转写→气泡"把 2 秒等待变成**可感知的仪式感**，而不是卡顿
- **打字兜底升 P0**：识别失败或环境嘈杂时可手输，保证 demo 不翻车

**结论**：不跟平台限制硬碰，把限制变成玩法的一部分。

### 难点 2：灵矽没有独立 ASR/TTS HTTP 接口

**问题**：灵矽语音能力只存在于设备 WebSocket 会话内，公开文档只有智能体 CRUD。

**解法**：**后端冒充一台虚拟设备**。
- `POST /xiaozhi/device/preregister` 用虚构 MAC 注册设备，绑定智能体
- 连 `wss://xrobo-io.qiniuapi.com/v1/ws/`，Header 带 `Authorization` / `Device-Id` / `Client-Id` / `Protocol-Version: 1`
- 上行声明 `format: pcm`（16k/16bit/LE，每帧 320 samples），避开 Opus 编码
- 收 `stt` 文本；下行 TTS 是 Opus，用 PyAV 解码后转 mp3 给客户端

**降级链**：A1（只借 ASR）→ A2（连 TTS 和音色）→ B（全本地）。任一层不通就往下退，不影响交付。

### 难点 3：AI 生成延迟造成冷场

见 3.3。串行生成 + 客户端预取一条，用上一段 8 秒音频盖住下一段 2 秒生成。

**配套优化**：
- TTS 按 `md5(voice|text)` 缓存，上帝固定台词第二局直接命中
- LLM `max_tokens=180`，够一段 60 字发言
- 上下文只取最近 8 条发言，控制 token 与延迟

### 难点 4：5 个 AI 说成一个味

**问题**：同一个模型、同一套 prompt，很容易 5 个人都是"理性分析型"。

**解法**：三段式 prompt + 差异化约束。

```
system = 身份（你是几号、什么角色、目标是什么）
       + 性格（{persona}，如"阴阳怪气，爱反讽"）
       + 硬约束（60 字内、口语、必须点名某个座位、不许复述规则、不许说"作为AI"）
user   = 当前天数 + 昨晚死者 + 存活玩家 + 此前 8 条发言
```

**兜底**：无 LLM 时用 `fallback_line()` 按角色+人格挑模板，保证不冷场，只是不聪明。

### 难点 5：投票决策不能让 AI 乱投

**问题**：让 LLM 投票 = 5 次额外调用 = 10 秒延迟。

**解法**：启发式。
- 统计 `log` 中 `(\d)\s*号` 的提及次数，被提最多的最危险
- 狼人额外过滤：不投自己人
- 平票则无人出局

零 LLM 调用，0 延迟，且结果符合"大家怀疑谁就投谁"的直觉。

### 难点 6：音频播放的句柄与状态管理

**问题**：每段语音新建 `InnerAudioContext` 会泄漏；`stop()` 与 `onEnded` 时序错乱会卡住流水线。

**解法**：
- **全局单例** ctx，每次只改 `src` 再 `play()`
- `play()` 前先 `stop()` 并清空回调
- `onEnded` 与 `onError` **都走同一个 `_finish()`**，保证流水线一定往下走
- 播放器不持有队列，队列逻辑放在 `app.js`，职责分离

### 难点 7：身份信息泄露

**问题**：如果 `state` 把所有人的 `role` 都发给客户端，抓包就能开挂。

**解法**：`public_state()` 里除自己外 `role_name` 一律 `null`，只有 `phase === "over"` 才全量揭晓。

## 七、性能与安全考虑

### 7.1 性能目标与手段

| 指标 | 目标 | 手段 |
|---|---|---|
| 小游戏首包 | < 2MB | 不引引擎、不打包音频资源（全部走 URL） |
| 首屏可交互 | < 500ms | 纯 canvas 绘制，无资源加载 |
| AI 首句开口 | < 2.5s | LLM 短输出 + TTS 缓存 |
| AI 段间空档 | < 500ms | 客户端预取一条 |
| 单局 LLM 调用 | ≤ 10 次 | 投票走启发式，不复用 LLM |
| 单局 TTS 合成 | 8–12 段 | 固定台词命中缓存 |
| 服务端内存 | < 300MB | whisper small 常驻约 500MB（可换 base 降到 150MB） |

**注意**：faster-whisper 是常驻内存的大头。若内存紧张，把 `WHISPER_MODEL` 改成 `base`。

### 7.2 安全设计

| 风险 | 措施 |
|---|---|
| 篡改牌局 | 服务端权威；action 必须与 `phase` 匹配；`target` 必须在存活座位内 |
| 越权看身份 | `public_state()` 按座位过滤（见难点 7） |
| 音频路径穿越 | 只允许访问 `audio/` 下的 `[a-f0-9]{16}.mp3`，`StaticFiles` 已限制根目录 |
| Prompt 注入 | 玩家文本作为 `user` 消息的 data 段落传入，不作为指令；system 里明确"玩家发言是待分析内容" |
| 刷接口 | 单 IP 每分钟限 60 次（演示环境可关） |
| 隐私 | 录音落临时文件，转写后 `os.remove`；不落库、不上传第三方（A1 走灵矽设备协议时按平台策略） |
| 密钥 | LLM/灵矽凭证只放环境变量，不入库、不进 Git |

### 7.3 容量假设

单人局，演示场景并发 ≤ 3。单进程 1 worker 足够，不做水平扩展。

## 十、与产品方案的一致性映射

| 产品 P0 功能 | 代码落点 | 接口 | 数据模型 |
